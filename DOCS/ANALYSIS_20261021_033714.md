## 2. Top issues, ranked by impact

### #1 — HIGH · The lob solver aims cross-court, but the spec says straight lane only
- **Where:** `src/squash/ShotController.js:273` (`targetCornerSign: -playerSideSign`), consumed at `:420-424`.
- **Evidence:** CHECKLIST TASK-27 says *"straight lane only, lateral target `x = sideSign · 2.35` … (cross-court measured side-wall-bound — do not implement)"*. The working tree passes `-playerSideSign`, so the front-wall aim and the corner reference `(±2.35, 4.2)` are on the side opposite the hitter, which makes it a cross-court lob. The STAGING draft passes `playerSideSign` (`STAGING…/ShotController.js:374`). The two drafts disagree, and the working tree matches the old cross-court code rather than the spec.
- **Impact:** the bring-up measurements say the cross lane runs into the side wall. That makes `LEGAL_CORNER` rare, so most lobs fall back to `ATTEMPT_SHORT` or `ATTEMPT_OUT`, which is the §5.7 failure mode the task is meant to remove.
- **Fix:** pass `playerSideSign`. If cross-court lobs are wanted later, make them an explicit `isCrossRequest` variant.

### #2 — HIGH · AI error modes overwrite the solved lob after the fact, so `solveStatus` is stale
- **Where:** `ShotController.js:~357-372` (the `aiErrorMode` block that rewrites `vel.y`) runs *after* `solveCornerLob`. The lob is tagged at `:392-396` and `:411-413`. The trigger is `src/squash/OpponentAI.js:468-479`: `lob` counts as `isHighOrHardShot`, so it gets `aiErrorMode = 'OUT'`.
- **Evidence:** on an AI OUT roll, `vel.y` is recomputed toward a 4.71–5.03 m target, but `solveStatus`, `solvedContactY` and the HUD grade still describe the solved trajectory. The HUD then shows `OVERHIT OUT! • LOB LEGAL_CORNER @ 4.3M` (`game_engine.js:3124`).
- **Impact:** the HUD and telemetry report the wrong result. It also breaks §5.9 principle 4 / TASK-29: errors should perturb the solve outputs, and the error layer should never pick the out surface.
- **Fix:** skip the `vel.y` override for `HIGH_LOB`, or re-classify after any override. TASK-29's perturbation model would replace this block properly.

### #3 — MEDIUM · The fallback tie-break always prefers ATTEMPT_OUT over ATTEMPT_SHORT
- **Where:** `ShotController.js:515-536`.
- **Evidence:** if *any* candidate's front-wall contact is ≥ 4.57, the solver takes the max-carry out shot. It never compares that against the best short candidate. The spec says *"highest corner-closeness score wins overall"*.
- **Impact:** from mid-court at high charge, the solver will pick a lob that goes out over one that lands short but is in play. That isn't how a player would choose, and it gives away free points.
- **Fix:** rank all non-objective candidates by `cornerDist`, then label the winner OUT or SHORT based on its contact height.

### #4 — MEDIUM · Two conflicting TASK-27 drafts, backup files, and a stale codegraph index
- **Where:** `STAGING_shot-law-wip-20261021-025312/`, 31 `*.bak.*` files, `.codegraph/`.
- **Evidence:** `codegraph_explore` for `solveCornerLob computeShotExecution` gave back the **STAGING** copies first (`STAGING…/ShotController.js:89,230`) instead of `src/`. The drafts differ in sign (#1), default charge (`0.8` vs `0.45`), `envelope` guard style and return shape (`undefined` vs `null`).
- **Impact:** agents and tools can read or edit the wrong copy, and it's unclear which draft is canonical.
- **Fix:** choose one draft and delete or archive the other. Add `*.bak.*`, `STAGING_*/` and `.codegraph/` to `.gitignore`, or move backups out of the tree.

### #5 — MEDIUM · `npm run lint` checks nothing in `src/`
- **Where:** `tsconfig.json` (`"allowJs": true, "checkJs": false`) and `package.json` (`"lint": "tsc --noEmit"`).
- **Evidence:** every source file is `.js` and `checkJs` is off, so `tsc` only checks `vite.config.ts`. Every CHECKLIST accept step relies on "lint exits 0", which passes no matter what the JS contains. A wrong import name or a typo'd field would still pass.
- **Fix:** enable `checkJs` (or add `// @ts-check` per file), or add ESLint with `no-undef` and `import/named`. As a cheap stopgap, add `node --check` or a Vite build to the accept steps.

### #6 — MEDIUM · Minified build output committed as source
- **Where:** `src/hud_ui.js` (26 KB on 2 lines), `src/mii_body_animation.js`, `src/mii_facial_fx.js`, `src/racket_kinematics.js` (1 line each), and `src/mii_model_overhaul.js`.
- **Evidence:** the files use mangled identifiers (`import*as i from"three"`, `const U=new e.Vector3(...)`). codegraph can't map their internals usefully, diffs on them can't be reviewed, and TASK-31 is supposed to edit `src/hud_ui.js`.
- **Impact:** TASK-31 work in `hud_ui.js` can't be reviewed, and the HUD timing-popup path that shows `solveStatus` is opaque.
- **Fix:** recover the original sources if they exist. Otherwise run them through a formatter once and commit that as the new baseline.

### #7 — LOW-MEDIUM · The lob solve costs 24 trajectory simulations per strike, synchronously
- **Where:** `ShotController.js:447-452`. Each call to `BallPhysics.simulateTrajectory` (`BallPhysics.js:254`) runs up to 336 steps at 120 Hz over 2.8 s, so one lob is ~8k physics steps plus allocations (a `Vector3` clone per sample).
- **Evidence:** it runs inline on both the player path (`game_engine.js:3017`) and the AI path (`:3156`), inside the frame where contact happens.
- **Impact:** probably a few ms on desktop, but it could cause a visible stall on low-end mobile at the moment of contact. Nothing is cached even though the inputs are deterministic.
- **Fix:** pass `{ maxTimeSec: 1.6 }`, since the first bounce happens well before that, and stop each sim early once `firstFloorBouncePos` is set. Measure it before tuning further.

### #8 — LOW · The HUD grade string grows without bound
- **Where:** `ShotController.js:392-396` → `game_engine.js:3124`.
- **Evidence:** the grade becomes `"<label> (<grade> • LOB LEGAL_CORNER @ 4.31M)"` and ends up in the popup. This combines with the AI suffixes `(TIN ERROR)` / `(OVERHIT OUT)`.
- **Fix:** keep `timingGrade` as it was and render `solveStatus` as a separate HUD field. The return object already exposes it.

### #9 — LOW · Leftover Argon branding (TASK-33 not done yet)
- **Evidence:** 65 `argon`/`Argon` matches in `src/` and `index.html`, and `package.json` is still named `"argon-tennis"`. This is expected because TASK-33 is open. It's listed only so it gets counted in that task's grep.

### #10 — LOW · God-object concentration in `game_engine.js`
- **Evidence:** `game_engine.js` is 4,161 lines and 152 KB, about 34% of all JS. It holds input dispatch, shot execution for both actors, prediction (4 separate `simulateTrajectory` call sites at `:2557, :2956, :3076, :3205`), difficulty tuning and HUD wiring. `audio_engine.js` (2,001) and `motion_controls.js` (2,036) are also large. TASK-30 and TASK-31 both edit this file.
- **Fix (longer term):** pull out a `StrikeExecutor` covering both actor strike paths and the trajectory-prediction refresh. That removes duplicated logic and narrows the conflict surface for same-file tasks.

## 4. Things checked and found sound
- `SHOT_CHARGE_ENVELOPES.LOB` exists in `TuningConfig.js:132` with the values TASK-26 specifies, so the fallback constant is only a safety net.
- `simulateTrajectory` returns the fields the solver reads: `events[].surface === 'front_wall'`, `samples[].pos/t`, `firstFloorBouncePos`, `finalPos`.
- Passing `tuningStoreRef = null` gives the same temperature factor as the store (`BallPhysics.js:24-26` vs `TuningConfig.js:264-267`), so the solver predicts the same physics the live ball uses.
- The search space matches the spec: 8 elevations × ≤3 paces = ≤24 evaluations, elevation as the outer loop, deterministic order. The T-band clearance is measured post-wall only (`sample.t > frontEvent.t`), as specified.
